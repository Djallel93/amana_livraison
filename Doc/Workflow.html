Phase 01

⚙️ Configuration initiale

La configuration est à réaliser une seule fois avant la première utilisation, puis à mettre à jour si les APIs ou le QG changent. Tout est accessible via le menu 📦 Gestion Livraisons AMANA → ⚙️ Configuration.

⚠️
Sans clés API valides, les formulaires de génération et de planification refuseront de s'ouvrir avec un message d'erreur. Configurer les APIs en premier lieu est obligatoire.

Paramètres à saisir manuellement

API_FAMILLES_URL · API_FAMILLES_KEY
Endpoint et clé d'authentification de l'API Family Management v2.2
API_BENEVOLES_URL · API_BENEVOLES_KEY
Endpoint et clé de l'API Volunteer Management v1.0
API_GEO_URL · API_GEO_KEY
Endpoint et X-Api-Key de l'API AMANA GEO v5.0 (géocodage, distances)
HQ_ADRESSE · HQ_LAT · HQ_LNG
Adresse complète et coordonnées GPS du quartier général (point de départ/retour)
EMAIL_FROM_NAME · EMAIL_ADMIN
Nom d'expéditeur affiché dans les emails et adresse de l'administrateur pour les notifications
API_LIVRAISON_URL
URL de l'application web déployée (doGet/doPost) — nécessaire pour les QR codes et les boutons email
ADMIN_PHONE
Numéro de téléphone affiché dans le pied de page des emails bénévoles
STATS_EMAILS
Liste d'emails (séparés par virgule) pour l'envoi automatique du rapport de statistiques

Paramètres d'optimisation des routes

Paramètre Défaut Description
DISTANCE_PROXIMITE_KM 2,5 km Distance en-deçà de laquelle deux livraisons sont considérées "proches" et regroupées dans un même cluster
MAX_CLUSTER_DIAMETER_KM 5 km Diamètre maximal d'un cluster — empêche les routes trop allongées ou inefficaces
DISTANCE_CLUSTER_MAX_KM 15 km Distance maximale pour regrouper deux clusters dans une même route
OUTLIER_DISTANCE_KM 40 km Au-delà de cette distance, une livraison est considérée "outlier" et signalée pour traitement manuel
MIN_COMPACTNESS_RATIO 0,4 Ratio minimum de compacité d'un cluster (0 = allongé, 1 = parfait cercle)
SAME_BUILDING_THRESHOLD_M 50 m Seuil pour considérer deux adresses comme le même bâtiment (regroupement)

Véhicules temporaires

Un bénévole avec permis mais sans véhicule propre peut être jumelé à un véhicule temporaire (via la feuille vehicle_tmp). L'appairage est automatique : le véhicule le plus capacitaire est attribué au bénévole le plus ancien (par date d'inscription).

Phase 02

📦 Génération des livraisons

Menu : 📋 Livraisons → ➕ Générer Livraisons

💡
La génération est idempotente : si une famille possède déjà une livraison active (non livrée, non annulée), elle est automatiquement ignorée. Pas de doublons possibles.
1

Saisie des filtres Manuel

Dans le formulaire, sélectionner : niveaux de priorité (1–5), types d'aide (Zakat El Fitr / Récolte / Ponctuelle), quartiers cibles, date de livraison et nombre maximum de familles.

2

Appel API Familles Auto

Le script appelle allfamilies avec les filtres. Les familles sont triées par criticité, puis filtrées par quartier si nécessaire. Résultat : liste d'objets famille avec adresse, nombre d'adultes/enfants, besoins spéciaux.

3

Géocodage batch Auto

Les adresses sont envoyées par lots de 100 à l'endpoint batchgeocode de l'API GEO. En cas d'échec batch, un fallback séquentiel est lancé adresse par adresse. Les coordonnées GPS (lat/lng) sont stockées dans la feuille Livraison.

4

Calcul de distance & tri Auto

Pour chaque livraison, la distance au QG est calculée via l'API GEO. Les livraisons sont triées par distance décroissante puis par priorité croissante avant d'être écrites dans la feuille.

5

Écriture en feuille Auto

Les lignes sont insérées en batch dans la feuille Livraison avec le statut Non Assignée. La fenêtre de disponibilité est définie de 09h00 à 18h00 par défaut sur la date choisie.

🚨
Feuille de conditionnement en avance : Si la feuille de préparation est générée avant la planification des routes, toutes les livraisons marquées "Prête" au conditionnement feront passer la route directement au statut "Prête" lors de sa création — sans action supplémentaire.
Phase 03

🗺️ Planification des routes

Menu : 🗺️ Routes → 📍 Planifier Routes

Algorithme de clustering

1

Sélection date & bénévoles Manuel

Choisir la date, l'occasion, le poids moyen par personne (domicile / hôtel), et cocher les bénévoles à mobiliser. Le tableau affiche leur statut du jour, véhicule et capacité en kg. Les bénévoles avec véhicule temporaire sont inclus automatiquement (icône 🔑).

2

Clustering géographique Auto

Les livraisons du même bâtiment sont d'abord fusionnées. Ensuite, l'algorithme crée des clusters en respectant le diamètre maximum, la compacité minimale, et en favorisant les livraisons du même quartier.

3

Attribution Best-Fit & Split Auto

Chaque cluster est assigné au plus petit véhicule capable de le porter (poids + nombre de parts + limite de livraisons). Si aucun véhicule ne convient, le cluster est découpé séquentiellement. Un garde-fou empêche les boucles infinies.

4

Optimisation TSP Auto

Pour chaque route de plus d'une livraison : algorithme du Plus Proche Voisin depuis le QG, suivi d'une amélioration 2-opt (inversion de segments pour éliminer les croisements). Réduction typique de 10–25% de la distance.

5

Génération du lien Google Maps Auto

Un lien Maps est construit avec le QG comme origine et destination, et toutes les livraisons (dédupliquées par coordonnées) comme waypoints. Le lien est stocké dans la feuille routes.

6

Écriture en feuilles Auto

La route est créée en statut Brouillon dans la feuille routes. Les étapes ordonnées (avec un stop de retour QG en dernière position) sont insérées dans etapes_route. Les livraisons passent au statut Assignée.

✅
Réorganisation manuelle possible : Menu 🔧 Réorganiser Étapes explique comment modifier manuellement la colonne ordre_passage dans la feuille etapes_route pour ajuster l'ordre de passage. Le lien Maps peut être régénéré via 🗺️ Régénérer Liens Maps.
Phase 04

🏷️ Conditionnement des colis

Cette phase se déroule en parallèle des phases 3 et 5, typiquement la veille ou le matin de la livraison. Deux outils sont disponibles.

📋
Feuille de préparation
Menu : 📦 Feuille de Préparation

Génère un Google Sheet avec pour chaque livraison : ID, hôtel ou non, nombre de personnes, besoins spéciaux, et un QR code unique. Quand l'équipe scanne un QR, le colis passe au statut "Prêt".
🏷️
Étiquettes imprimables
Menu : 🏷️ Générer Étiquettes

Génère un Google Sheet avec recto (ID route, famille, part X/N) et verso (QR de confirmation). Format A4, densité configurable (ex. 7×3 = 21 étiquettes/page). Impression recto-verso bord long.

Automatisme de validation

1

Scan du QR code Manuel

L'équipe scanne le QR de chaque colis. Une requête HTTP est envoyée à l'API Web (update_stop_status) — sans token, cet endpoint est ouvert pour l'accès interne.

2

Mise à jour statut_conditionnement Auto

La colonne statut_conditionnement de la livraison passe à "Prête". Un trigger onEdit installable surveille aussi les modifications manuelles de cette colonne dans la feuille.

3

Vérification de la route complète Auto Trigger

Après chaque scan, le système vérifie si toutes les livraisons de la route associée sont conditionnées. Si oui, la route passe automatiquement au statut "Prête" et l'email d'itinéraire est envoyé au bénévole.

⚠️
Timing important : Si la feuille de conditionnement est générée avant la planification, les étapes n'existent pas encore. Le statut est conservé sur la livraison et vérifié automatiquement lors de la création des stops à l'étape de planification.
Phase 05

✉️ Confirmation & expédition

1

Confirmation manuelle des routes Manuel

L'admin revoit les routes en statut Brouillon ou Prête dans la feuille routes et change le statut à "Confirmée". C'est le gate-keeper avant l'envoi des emails.

2

Envoi des emails Manuel Trigger

Menu : ✉️ Envoyer Routes aux Bénévoles. Sélectionner les routes confirmées à envoyer. Le système génère (ou réutilise) un token de 32 caractères valide 48h par route.

3

Contenu de l'email Auto

L'email est construit en HTML responsive optimisé mobile, avec : bouton Maps, bouton ▶ Démarrer, une carte par livraison (adresse cliquable, téléphones famille, boutons ✅ Livré / ⏭️ Ignoré), bouton 🏁 Terminer, et numéro d'urgence de l'admin.

Logique des tokens

Condition Comportement
force_active = true Token toujours valide, ignorant la date d'expiration. À utiliser pour des tests ou des routes à durée indéterminée.
force_active = false + date non expirée Token valide — accès aux actions.
force_active = false + date expirée Token invalide — page d'erreur affichée au bénévole avec message "Lien expiré".
Token inexistant ou manquant Retour d'une page HTML d'erreur "Lien invalide".
Phase 06

📊 Suivi en temps réel

Toute l'interaction bénévole se fait via l'API Web (doGet/doPost). Chaque clic sur un bouton email envoie une requête HTTP avec token + action.

Actions disponibles via l'API Web

Action Token requis Effet
ping Non Test de connexion, retourne version et timestamp
start_route Oui Route → En Cours. Tous les stops En Attente / Prêts → En Cours
confirm_delivery Oui Stop → Livrée, Livraison → Livrée, heure_fin enregistrée
skip_delivery Oui Stop → Ignorée, commentaire ajouté, notification email admin
finish_route Oui Vérifie que tous les stops sont traités, Route → Terminée, Token expiré
update_stop_status Non Met à jour statut_conditionnement d'une livraison (usage interne conditionnement)
⚠️
Livraisons ignorées : Quand un bénévole ignore une livraison, une notification email est immédiatement envoyée à l'admin (EMAIL_ADMIN) avec le détail de la famille, l'adresse et des suggestions d'action (réassigner, contacter).

Statistiques

Menu : ⚙️ Configuration → 📊 Statistiques. Le tableau de bord affiche en temps réel :

  • Nombre de livraisons / routes / bénéficiaires
  • Taux de complétion avec barre de progression et graphique camembert par statut
  • Comparaison poids donné / livré (routes) / calculé (parts × poids moyen)
  • Détail par route (distance, poids, nb livraisons, statut)

Un bouton ✉️ Envoyer par email diffuse le rapport aux destinataires configurés dans STATS_EMAILS. Un envoi planifié automatique est aussi possible via la fonction sendScheduledStatsEmail() (à configurer comme trigger Google).
